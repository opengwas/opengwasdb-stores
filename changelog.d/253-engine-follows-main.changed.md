- **The `opengwasdb` engine follows `main`, and `pixi.lock` is the only place its commit is written (issue #253).** `pixi.toml` names `branch = "main"`; the lock resolves it to `v0.3.3` (`1f1e289`), whose `opengwasdb/` code is identical to `v0.3.2`'s. `PINNED_OPENGWASDB_REVISION`/`_TAG` and `pixi.toml`'s bump log are gone. One module, `ogstores.engine`, says which engine an executable is (commit and version from its own install) and which commit the lock resolves, parsing every opengwasdb lock entry and refusing none, two, or a malformed one.
  - `pixi run engine-update` relocks to `main`'s tip, installs it, checks every store-build environment runs the locked commit and writes the accepted Store format, and puts the old lock back on any failure; `--check` changes nothing. `env-check` prints the locked and installed engine.
  - Manifest Generation's resolve stage refuses an engine other than the locked one, in the release guard's words.
  - Step records and `validation.yaml` no longer pair the executable's commit with the interpreter's version: a step record's version comes from the executable it ran, `register` takes `build_environment` from the phase's step records rather than `PATH`, and the yardstick records the engine its workers import rather than the lock's commit.
  - Strict only where a step continues another engine's output (#410): an interrupted `complete-dense` resumes only under the engine its start record names, and a start record from before this change, which names none, resumes only when every step record of its phase names the installed engine. Every other step may run under a newer engine of the same Store format, so re-running `validate` or adding an Indexed Variant Subset after `engine-update` needs no rebuild. `register` records every engine a phase used in `validation.yaml`'s new `build_environment.engines` (commit, version and the steps each ran); `opengwasdb_commit` and `opengwasdb_version` keep naming the engine that wrote the Store, and `validator.version` names the engine that ran `validate`.
  - A candidate's resolver engine survives acceptance as `acceptance.resolver_engine`, and a build under another engine adds a warning naming both.
