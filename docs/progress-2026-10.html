1 · Performance

Build, completion and query cost across the three store shapes

One store format, three layouts. The layout is chosen per release to fit how the source data is shaped.

Dense

Every Analysis on one shared variant axis. For full GWAS batches: FinnGen R13, UKB-B.

Ragged

Each Analysis keeps only its own variants. For sparse molecular QTL and metabolite GWAS: eQTLGen, Chen 2023, Sun 2018.

Hybrid

A Dense block over a reference panel, plus an Overflow for each Analysis's off-panel variants. For heterogeneous GWAS Catalog studies.

Build cost at full scale step records · /data/opengwasdb/stores/*/records

Wall time for every executed step of each full-scale release, as recorded by the release workflow on the production host (224 cores, shared). Workers are the --n-workers the bundle's build.yaml declared.

build or completetop hitsvalidate

Peak memory is not in the step records. The paired pilot builds measured for opengwasdb #249 give the order of magnitude: Dense, 10 UKB-B Analyses on 4 workers, 8 min 27 s at 9.7 GiB peak; Hybrid, 10 GWAS Catalog Analyses, 43 min 31 s at 19.3 GiB; Ragged pilots, 5 to 7 s at about 2 GiB.

Reference completion OGS-00009 → OGS-00010 · complete-dense

Completion is a separate release that depends on its parent. It imputes missing cells from a reference LD panel (EUR, HGDP+1kGP hg38, 1,357 LD blocks) and marks every imputed cell as imputed, so observed and imputed values are never confused.

Where the 27.4 billion cells of the completed UKB-B store come from

Ragged completion runs in the workflow too: OGS-00001 → OGS-00002 (eQTLGen pilot, 10 Analyses) took 67 s and grew 86,376 variants to 207,764, with 106,653 imputed associations. Hybrid completion (complete-hybrid) exists in opengwasdb but has not yet been run on a registered release.

What 0.2.0 buys. Whole-Analysis reads are 3 to 4 times faster with a tenth of the memory on Dense (UKB-B 27.7 s at 11.8 GiB → 6.5 s at 1.0 GiB). Hybrid window and lookup queries drop from minutes and up to 59 GiB to seconds and under 5 GiB. Each store has about 100 times fewer files, for 1.4 to 2.6 % more bytes.
What it costs. Point queries that were already fast got slower in absolute terms: top hits 1 → 11 ms, single-variant PheWAS 5 → 46 ms on UKB-B. The one shape slower by more than a second is the Hybrid Overflow PheWAS of an off-panel variant (22.6 → 29.0 s). A variant-centric index (ADR 0060) is the planned fix.

2 · Storage footprint

How 37 bytes become 2

FinnGen publishes each association as a row of gzipped text, which costs about 37 bytes per association. OpenGWASDB holds the same association in 2.16 bytes, everything included. No single trick does this. Each value in the source row is either written once where many rows can share it, recomputed when it is read, or encoded as a small difference from something the store already holds.

What one cell costs

z · int16 · 2 bytes
SE · int8 · 1 byte
EAF · int8 · 1 byte

Four bytes before compression. Zarr then compresses each chunk with Blosc Zstandard and bitshuffle. Bitshuffle groups bit k of every value in a chunk together, and the high bits of a typical z are almost always the same, so the long runs compress very well. FinnGen's three planes average 2.11 bytes per cell on disk.

Three encodings, each against something the store already holds

z · 16-bit fixed point

Every z gets the same absolute precision, so p-values stay accurate for the strongest signals. A float16 does the opposite: its step doubles as z grows. Values beyond ±32 go into a small exact table. Nothing is clipped.

SE · 8-bit residual from a line

Within one Analysis, SE is almost entirely set by allele frequency: SE ≈ σ / √(2·EAF·(1−EAF)·N). Each Analysis stores two numbers for that line, and each cell stores only its 8-bit distance from it. N and the phenotype SD sit inside the intercept, log σ − ½ log N.

EAF · 8-bit residual from the variant's baseline

Endpoints from one cohort report nearly the same frequency at a variant. The store keeps one baseline per variant (the median across its Analyses, in logit units), and each cell stores an 8-bit difference from it.

Residual spread, sd of the logit residual. The baseline must be the store's own: against the EUR reference panel, FinnGen frequencies differ by up to 3,000× (the Finnish founder effect).

Each encoding is chosen by measurement when the store is built, and is never a fixed default. The builder tries residual ranges of ±0.5, ±1 and ±2 and keeps the smallest one that holds exceptions to at most 2 % in every Analysis and actually saves bytes. Otherwise it writes the plane as float16 or float32. The choice is declared in manifest.json, and readers decode only what is declared. FinnGen chose ±2 for SE and ±0.5 for EAF; UKB-B chose ±0.5 for both.

Where FinnGen R13's 126.6 GB goes bytes on disk by component

One variant axis, chunked for the queries people run

A Dense store is a grid of variants × Analyses for each statistic. Zarr cuts each grid into inner chunks of 1,000 variants × 64 Analyses, which is the unit a query reads and decompresses. Format 0.2.0 packs the inner chunks into shards of 100,000 × 1,024, the unit stored as one file. Small indexes beside the grid tell a query which chunks it needs. Pick a query shape:

inner chunk (read unit)shard (one file)read by this querySchematic. FinnGen's real grid is 21,231 × 44 inner chunks in 213 × 3 shards per plane.

Fewer files. In format 0.1.0 every 1,000 × 1,000 chunk was its own file, 237,464 files for FinnGen. Format 0.2.0 reads narrower inner chunks but stores them in shards: 2,399 files for 1.7 % more bytes.

Ragged and Hybrid use the same three encodings. A Ragged store keeps, for each Analysis, a run of (variant index, z, SE, EAF) for the associations it actually has. It pays for a variant index on every association but nothing for absence: the Chen metabolome store holds 58 M associations in 1.30 GB. Hybrid is a Dense block over a reference panel plus a Ragged Overflow for off-panel variants.

4 · Store build pipeline

Two workflows that meet at a frozen Release Bundle

Phase B turns a source collection into a candidate Release Bundle. A person reviews and accepts it. Phase A builds the accepted bundle into a Store Release. They share no DAG on purpose: a change upstream must never silently regenerate an accepted bundle and rebuild a 127 GB store.

Metadata curation runs alongside the build. Canonical EFO trait mapping for UKB-B now resolves 553 of 2,514 Analyses (22 %) after two rounds (an embedding retriever plus an LLM chooser, with Showcase context). 845 labels wait in the review queue.

The bundle is the build instruction

A Release Bundle is four small files plus evidence sidecars. build.yaml names an opengwasdb subcommand, and its option keys are passed through as flags verbatim. The registry keeps no copy of the parameter schema, so nothing can drift. On the right is the command the workflow actually ran for OGS-00011, taken from its step record.

release.yaml      identity, status, lineage, source snapshot
build.yaml        the recipe
analyses.tsv      membership (opengwasdb owns the schema)
validation.yaml   evidence written back by the run

Two production runs, step by step from each step's record

The tracked output of every Snakemake rule is the step's record file, never the Store directory, so a half-written Store cannot satisfy a rule. A completed release declares its parent's register record as an input, which is why OGS-00010 waits for OGS-00009.

  • Safe re-runs. pixi run release holds a lock per release, finishes any publication a crash interrupted, and refuses to rebuild a published release unless asked with --config force=1. A forced run archives the old Store under replaced/<UTC>/ and deletes nothing. OGS-00005 was the first release replaced this way, on 8 Oct.
  • Portable bundles. The artifact root comes from deployment configuration, not from the bundle, so one immutable bundle builds on CI, a laptop or the production host.
  • Generated index. pixi run index regenerates STORES.md, stores.tsv and the by-label/ links from the bundles. The opaque OGS- id is the only identifier.
5 · Stores built so far

Twelve Store Releases on the production host

Counts come from each Store's own manifest and sizes from the bytes on disk. Wall time is the sum of the recorded steps. Every Store passed opengwasdb validate in its run. The registry status lags the artifacts: OGS-00008 to 00011 and OGS-00016 are built and registered on /data, but their records have not yet been committed back to stores/.
