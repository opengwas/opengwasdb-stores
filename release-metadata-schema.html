Release Bundle schema

A Store Release is defined by a small, self-contained Release Bundle: one directory per release under stores/, whose files record identity, membership, the Build Recipe, and (once built) validation evidence. The bundle is the output of Phase B and the fixed input of Phase A; see docs/spec/store-release-workflow.md for the workflow that consumes it and the ADRs it is governed by.

bundle.check() in src/ogstores/bundle.py is the executable definition of a valid Release Bundle. It accumulates every registry-side error it can find and never raises for invalid bundle content, so an author can run it and fix everything in one pass:

pixi run bundle-check        # discovers and checks every stores/<id>/ bundle

The contract holds only what both workflows share and what Store Release Build needs to consume a bundle. Manifest Generation’s own rules for a candidate’s analyses.tsv live beside it, in src/manifest_generation/generation_rules.py (#250): the columns a generator must resolve, and how it records the INFO and MAF filters it requests. The emitter runs them before a candidate lands, and pixi run bundle-check runs them with the contract over every committed bundle, so neither escapes CI.

A Release Bundle structure is:

stores/OGS-00042/
  release.yaml      identity, lineage, status, source snapshot, generation log, prose
  build.yaml        the recipe: an opengwasdb subcommand and its flags
  analyses.tsv      one row per Analysis; opengwasdb owns the shared schema
  summary.yaml      generated review view derived only from analyses.tsv
  validation.yaml   evidence, written back by the register step
  sidecars/         optional generated evidence (ancestry, SD, sparse regions)
  column_maps/      the Column Map a mapped Source Collection is read through

The store_id is the opaque OGS- identifier (ADR 0022). It is the directory name here and the directory name under the artifact root. In the built Store’s manifest it is the store_id, and the release_id of an Observed-Only release. A release that completes its own Store keeps store_id as the id once completed, and the completed Store carries release_id <id>-completed: a new release of the same Store (ADR 0037, opengwasdb ADR 0011). A two-id Reference-Completed child (ADR 0007) is the exception: its id is the release_id, and the store_id is its parent’s. There is no Store Family tier: the OGS- id is the only identifier (ADR 0028).

Large Release Artifacts live outside this repository, at a path that is a pure function of the identifier:

<artifact-root>/OGS-00042/
  source/                   acquired or filtered source files
  work/                     checkpoints, scratch, logs
  work/analyses.tsv         derived build manifest (exclude_from_build rows dropped)
  records/<step>.json       one per executed step
  store.opengwasdb          the Store Release
  store.opengwasdb.partial  transient staged destination
<artifact-root>/by-label/   generated symlinks

The artifact root is deployment configuration, not a bundle field: a bundle is immutable once accepted, so committing an absolute path into it would bind that bundle to one machine. paths.artifact_root() resolves it, highest precedence first, from a workflow --config artifact_root=, the OPENGWASDB_ARTIFACT_ROOT environment variable, the tracked ogstores.yaml, then the built-in default (/data/opengwasdb/stores). A Build Recipe must not declare an artifacts block (issue #126).

Pipeline stages

Phase B — what produces a bundle — is described here only in outline; the canonical command log for each release is recorded in release.yaml:generator.commands. A Manifest Generator conventionally has five stages:

Stage Purpose Typical inputs Outputs
discover Snapshot available upstream analyses and files. Source inventory, GWAS Catalog studies table, source meta.yaml, provider APIs. Raw candidate records and source-file locations.
select Apply the Store Release’s inclusion rules. Candidate records, generator config, priority lists, publication/analyte filters. Selected Analysis set for a proposed Store Release.
derive Add authoritative analytical metadata and generated evidence. Selected rows, provider metadata resolvers, source files, OpenGWASDB readers, reference resources, Ensembl, checksums. Resolved analyses.tsv columns and sidecar evidence.
emit Write a reproducible release bundle. Resolved rows, sidecars, build choices, generator provenance. release.yaml, analyses.tsv, build.yaml, validation.yaml, sidecars.
accept Check that the bundle is complete enough to build. Release bundle, schema checks, lightweight source/readability checks. Updated validation.yaml and release status.

Metadata resolution and summary-statistics reading are orthogonal concerns. A Source Collection chooses a provider-specific metadata resolver for study tables, APIs, or endpoint manifests, and separately declares an OpenGWASDB Source Reader Capability for source data. The resolved metadata shape is common even when the provider and source format differ.

release.yaml

Registry identity and provenance. Never read by opengwasdb. Required for an accepted Release Bundle; a candidate may leave lifecycle timestamps null.

The file trims to identity, lineage, Release Status, creation time, source snapshot identity, the generation command log, and the prose that explains the Store Release (issue #136, ADR 0029). Issue #137 removed the one-time migration provenance block (ADR 0030); the published artifact path is now a pure function of the identifier.

Field Required Description
store_id Yes Opaque OGS- 5-digit identifier (ADR 0022): the directory name under stores/, and must match it.
label Yes Source-natural display name; provenance, never an identifier (ADR 0022).
association_coverage Yes What associations the Store holds, in one vocabulary shared with opengwasdb: gwas (genome-wide), cis (a cis window around each Analysis’s target only), cis_and_signals (a cis window plus significant signals elsewhere) or signals_only (significant signals and their flanks, no cis window). It replaced full_gwas and cis_plus_signals (issue #341, ADR 0040). bundle.check() refuses any other value and a value that is not a string, and Bundle.association_coverage raises rather than answering a default, because the Analysis Catalog shows it and counts Analyses by it. It is also the value plan() passes to a Ragged build as --association-coverage (issue #341), so it is declared, never inferred from the Store Layout. A Dense or Hybrid release can carry only gwas, and bundle.check() refuses any other value there (opengwas/opengwasdb#298). A region-filtered release declares cis_and_signals or signals_only and must agree with its region_policy.association_coverage. Every committed bundle declares it.
access_posture No Declared availability category: public, controlled, or embargoed. The one store-level fact the retired Store Family tier genuinely declared (ADR 0028); every committed bundle declares it, but it is descriptive rather than structurally required.
status Yes Registry lifecycle state: candidate, accepted, built, validated, superseded, or withdrawn.

The registry’s YAML loader follows YAML 1.1, so the unquoted spellings true, yes and on (and false, no, off) are booleans; a quoted trial: "yes" is a string and trial: 1 is a number, and bundle.check() refuses both. A reader that does not gate on check() refuses them too rather than reading them as false: the Analysis Catalog’s serving policy excludes every Trial Store Release, and a coerced value would serve one.

It is a fact about the release, not a serving decision (ADR 0008).

accepted_at No Timestamp when the bundle was accepted as the release input record.
source_snapshot_id Yes Dated or provider-native source snapshot used for this release, for example a GWAS Catalog studies-table release date.
source_snapshot No Source snapshot identity detail. For a provider-manifest release: manifest_url, manifest_sha256, manifest_size_bytes, manifest_etag, manifest_last_modified.

generator.version No Generator package version, git commit, or script hash. A value beginning sha256: must carry a valid 64-hex digest.

bundle.check() requires exactly the keys marked Yes above and rejects a generator that is not a mapping or whose commands is empty. It holds association_coverage to its four-value vocabulary (issue #341, ADR 0040), and the descriptive facts the Analysis Catalog’s serving policy reads (ADR 0008) to a checked shape: trial must be a YAML boolean, and absent means false (a quoted trial: "yes" or a numeric trial: 1 is refused, and Bundle.trial raises rather than answer false); and superseded_by is present on exactly the superseded releases, and names a registered Release Bundle, like derived_from (issue #321). Release Status transitions are a separate, optional check (validate_status_transition): the legal lifecycle graph is candidate -> accepted -> built -> validated -> {superseded, withdrawn} with withdrawn reachable from every state. See the workflow specification’s “Status lifecycle and transitions”.

For a BESD build (build-ragged-besd), source_snapshot.besd_prefix is required and must be a non-empty string; its referenced files are deliberately not inspected, because monolithic BESD source identity is an unverified host path prefix (issue #134, a known integrity gap).

BESD file sets (#291): identity, resolution and verification. This is the one normative definition; the connector contract and the eQTLGen section link here. A BESD file set is .besd, .epi and .esi under one prefix, and holds an Analysis per probe. Its identity is each member’s own size and sha256, recorded in the Acquisition Manifest’s members (columns), with the .besd member’s size and sha256 standing for the set in the single-file bytes and sha256 columns; no composite checksum exists. The resolver manifest declares each Analysis with source_reader_capability opengwasdb.besd, source_file the file set’s prefix (no .besd, .epi or .esi) and a source_probe_id column naming its .epi probe. The column is required for a BESD row and refused for any other, and is blank everywhere else. checksum and size_bytes are the .besd member’s. Preflight holds every member the Acquisition Manifest records to its recorded size and names a missing or resized one. Because the prefix is not a file, a Resolution Record binds fingerprints.source_member_files (each member’s bytes and mtime_ns) and resolution_config.source_probe_id instead of a source file’s size and mtime, and Manifest Generation holds them against the files as they are when it verifies a record and when it preflights the frozen inventory. The resolver’s index.json also gains source_measurements: one entry per file set measured in that invocation (measurement_id, source_file, source_genome_build, the analyses that share it, and an error when the set could not be read), each measured once and shared by its probes’ records (diagnostics.ancestry_measurement_id). It is absent when every record resumed. The release’s source_snapshot.besd_prefix and source_genome_build are rendered from the resolver manifest’s prefix and the recipe’s source-build; the pipeline’s reader for build-ragged-besd is opengwasdb.besd, which the recipe cannot name because options pass to the command verbatim.

analyses.tsv

One row per Analysis, tab-separated. This is the membership record: the exact set of Analyses in the release. The shared interpretation-bearing core schema is owned by OpenGWASDB (ADR 0017); the registry may add registry-only columns needed to locate source files, record checksums, carry licence/publication provenance, or explain inclusion decisions. bundle.check() delegates the shared contract to the pinned opengwasdb.model.analyses module and adds registry-owned vocabularies on top.

Use empty strings for unknown optional values in TSV. Values are resolved after applying generator config defaults, even when that repeats store-level metadata.

Builders may ignore registry-only columns after using them to locate inputs. Store-only columns must not be required before the build has run. exclude_from_build is the exception that is enforced rather than merely ignored: the registry materialises a derived build manifest with every excluded row removed and points the builder at it, so opengwasdb never sees an excluded row at all (ADR 0025).

A bundle’s header carries these columns:

analysis_id  stored_effect_scale  sample_size_kind  sample_size_scope
sample_size  original_effect_scale  original_sd_method
ancestry_assignment_method  assigned_ancestry

The first eight are OpenGWASDB’s required set, which bundle.check() enforces through the pinned shared schema. assigned_ancestry is added by the registry and required by Manifest Generation’s rules, which also require ancestry_assignment_method, stored_effect_scale and original_sd_method (#250). bundle.check() enforces the shared required set, the retired-column list, and the ancestry vocabulary, case/control-count, and checksum rules below. The Required column in the reference table is the broader authoring convention for a complete bundle — columns marked Yes that check() does not itself demand (analysis_label, source_label, source_file, checksum, source_genome_build, license, trait_ontology_mapping_method) are what a reviewer and the pinned OpenGWASDB schema expect to see populated. Every required column must also be non-empty on every row, except that a release Store Release Build will not build and the two legacy trial releases OGS-00001 and OGS-00002 may leave required Analysis values blank (issue #134; see “Blank required values” below).

bundle.check() rejects any column named by the pinned upstream RETIRED_ANALYSIS_COLUMNS list: phenotype_id, phenotype_label, trait_id, gene_id, gene_name. The upstream schema is the single retired-column contract; the registry does not keep its own copy. It also rejects any analysis_id outside ^[A-Za-z0-9][A-Za-z0-9._-]*$, because the Analysis Catalog addresses an Analysis <store_id>:<analysis_id> and a client must be able to split that on : into its two parts (issue #319; see “Legacy analysis_id values” below). A Trait Ontology Mapping carries an ontology term and its trait label, never a gene identifier with an authority name standing in for the label: gene/target identity is annotation (analysis_label for a single-target Analysis; trait_chr/trait_bp and the target sidecar for the target itself). bundle.check() rejects a gene- or protein-shaped trait_ontology_id (Ensembl, HGNC, Entrez/NCBI Gene, UniProt) and the matching authority name in trait_ontology_label (issue #141). It checks each term of a list, so a gene identifier cannot hide behind an ontology term. The label is checked whole and never split, because a term’s own label may contain a comma (osteoarthritis, hip).

One split rule serves the contract and Manifest Generation alike (trait_ontology_id_terms): split on every comma and strip each part. A value is in canonical form only when its parts are all CURIEs and rejoining them with ", " gives the value back, so EFO:1,EFO:2, padding and empty terms are refused.

bundle.check() also rejects a trait_ontology_id term that is not a CURIE, such as a raw http:// URI (#286). OGS-00011 was accepted before this check with GWAS Catalog’s raw EFO and ORDO URIs in 2,972 rows. An accepted bundle is never rewritten, so those values are tolerated for that release by name (LEGACY_NON_CURIE_TRAIT_ONTOLOGY_RELEASES) and reported on check()’s second channel with their count. Every other bundle, buildable or not, is held to the CURIE form.

The four INFO columns are one policy: info_score_threshold is the requested floor and imputation_score_column/imputation_score_kind/ imputation_score_provenance are the exact source-column declaration it requires. A declared column is only meaningful to the GWAS-SSF reader, and the pinned OpenGWASDB validator reads the reader from the row, not from the Build Recipe’s source-reader-capability default. A declared Analysis with no usable score is retained: core no longer reports it as a controlled failure, the registry does not refuse it, and it is included with literal NaN INFO cells. Older bundles may omit all four columns entirely.

The MAF floor is a defaults.maf_threshold release decision applied per Analysis: an Analysis is exempt (and emits NaN) when its Source Metadata Table row’s genotyping_technology (;-joined, source order) is non-empty and every technology is in release_policy.maf_filter_exempt_genotyping_technologies; missing technology metadata is never an exemption. The column is a fact a source’s adapter writes (the GWAS Catalog’s from each -meta.yaml); the exemption is the release policy over it (#347). The resolver manifest carries the derived maf_threshold per Analysis and the resolver record’s maf_state plus its fingerprint binding decide the emitted candidate value, exactly as for INFO. Manifest Generation’s rules validate the column on every row, independently of the pinned OpenGWASDB Analysis schema.

A separate optional store_composition.require_maf_filtered generator-config rule decides whether a shared Store may admit an Analysis with no applied MAF floor. Absent or false, every otherwise admissible Analysis is included; true requires a positive defaults.maf_threshold and excludes an otherwise admissible Analysis whose emitted maf_threshold is NaN as not_maf_filtered (see the exclusions sidecar). The rule runs after every other membership decision and only at emit, so toggling it needs --stage emit and never a re-resolve. See ADR 0033.

A release whose Analyses each measure one molecular target – proteomics, such as Sun 2018’s SomaScan pQTLs – adds the target columns trait_chr, trait_bp, mhc, target_resolution_method and n_target_rows, rendered from the Source Metadata Table’s target annotation (#300; the retired R gwas-ssf-ragged generator also wrote n). A release with no such target (for example small-molecule metabolomics, issue #26) omits these columns entirely rather than filling them with placeholder or NA values — their absence is how a reviewer tells the two shapes apart. tissue and context likewise appear only in a release that declares them. These columns remain release-specific with no shared-core equivalent.

The target sidecar, sidecars/analysis_targets.tsv, lists each targeted Analysis’s target annotation (assay, gene symbol and Ensembl id, span, MHC flag, whether the assay is an aggregate, how the target was resolved); it is evidence, not duplicate Analysis columns. Bundles emitted by the R generator carry its wider form, with the raw SomaScan and Ensembl fields.

Accepted build rows

Accepted build rows must have usable sample-size metadata. Analyses with unknown sample size may appear in Source Inventories, candidate diagnostics, or review sidecars, but should not be included as buildable rows in an accepted analyses.tsv.

Case/control-style counts follow sample_size_kind, not the effect scale: an Analysis whose tier declares sample_size_kind = case_control carries n_cases and n_controls, and one whose tier declares any other kind leaves both blank. ukb-b is why the two are separate – its provider reports units: SD for binary traits too, so its case-control tier declares stored_effect_scale: sd beside sample_size_kind: case_control (#289). Most Sources pair them (log_or with case_control), which is why the scale looks like the deciding field. For time-to-event traits, n_cases is the event count and n_controls is the non-event or comparison count reported by the source. When the counts do not apply both must be blank rather than 0: zero is a real count, and writing it where the counts do not apply is exactly the absence-vs-zero confusion CONTRIBUTING.md rules out. bundle.check() rejects a non-empty count on a non-case-control Analysis (issue #133).

assigned_ancestry is one controlled vocabulary on every Analysis, regardless of ancestry_assignment_method: the ancestry-mixture reference’s super-population codes (AFR, AMR, EAS, EUR, MID, NAF, SAS) or empty for unassigned. It is never a free-text Source Ancestry Label (European, East Asian, and so on). The tracked translation from the candidates table’s free-text labels to these codes is resources/reference-resources/ukb-ancestry-mixture-hg38/source_label_map.tsv, read by both the Ancestry Assignment stage and the manifest generators so the two cannot drift apart. bundle.check() rejects any value outside the vocabulary, so the split cannot silently reappear.

Blank required values (issue #134)

bundle.check() normally fails a row that leaves a required column blank. Two deliberate exemptions exist, both narrow:

  • Releases Store Release Build will not build. A release whose status is not accepted, built or validated (#247) may leave values blank: a candidate is still being resolved, and what it must resolve before it lands is Manifest Generation’s policy, not the contract’s (#250). check() discloses the count as a tolerated gap cited not buildable.
  • Legacy monolithic BESD releases. OGS-00001 and OGS-00002 are exempt because their required Analytical Metadata is unpopulated in upstream BESD sources and cannot be resolved without external study metadata. The exemption is scoped to exactly those two named releases. Any new release — including any future ragged-BESD or completed release — must provide valid required values or fail bundle.check().

This is a known integrity gap, tracked by open issue #134, not an equivalent alternative to the per-Analysis checksums and source identity enforced for other formats.

Legacy analysis_id values (issue #319)

bundle.check() fails a row whose analysis_id is not one path segment, and names the row. OGS-00001 and OGS-00002 are exempt: they carry eQTLGen’s <probe>::<tissue> ids (ENSG00000175445::whole_blood), which an accepted bundle may not be edited to remove (ADR 0004), so check() discloses the count as a tolerated gap cited #319 instead of reporting it as an error. The exemption is scoped to exactly those two named releases. Every other release — including any future eQTLGen or other ragged-BESD build, which names its Analyses by bare probe id and records the tissue in the tissue column — must satisfy the pattern. Retire the guard in favour of opengwasdb.model.analyses.validate_analyses() if OpenGWASDB ever validates the column (ADR 0017).

A Dense or Hybrid Build Recipe may declare optional named Indexed Variant Subsets (stores #209). The Step’s durable records/indexed-subset-<name>.json is written by the ordinary step executor; no new record schema is introduced.

name Yes The subset identity. The consumer’s grammar [A-Za-z0-9][A-Za-z0-9._-]{0,127}, and the registry additionally refuses .. because the name becomes part of the record filename. Unique within the release.
resource_id Yes resource_id of a maintained kind: variant_list Reference Resource (resources/reference-resources/<id>/resource.yaml).
variant_list Yes The concrete canonical-ALID list path the build passes as --variant-list. It must match the resource declaration’s location. Recorded so the immutable bundle is self-contained; plan() never opens it.
reference_assembly Yes The list’s assembly, passed as --reference-assembly. It must match the resource declaration’s genome_build.

A value must render as CLI tokens – a string, number or bool, or a non-empty list of them; a mapping would arrive as its own repr and null or an empty list as nothing at all, so both are refused.

The key is optional; omit it to declare no subsets. An explicit indexed_subsets: null is malformed rather than treated as omitted, so a generator cannot silently drop a declaration.

    resource_id: hapmap3-hg38

The planner does not interpret the flag: it renders the mapping into the two build-indexed-subset steps, build phase and completion phase alike, exactly as declared.

bundle.check() validates the declaration shape (names, required strings, checksum syntax, uniqueness, Dense/Hybrid only, no overwrite, and options values that render as CLI tokens) without any resource I/O. See ADR 0034 and the workflow specification’s “Indexed Variant Subsets”.

Column Map binding

A tabular Source Collection read through OpenGWASDB’s generic tabular reader has a Column Map: a TOML file declaring which provider column supplies each field and the collection’s conventions (opengwasdb ADR 0063). ADR 0036 has it travel in the Release Bundle, checksummed, so Analysis Resolution and Store Release Build read every file the same way (#292).

An Analysis reads through a Column Map when its source_reader_capability is opengwasdb.column-map. A row that leaves source_reader_capability blank, or has no such column, inherits the Build Recipe’s build/complete options.source-reader-capability. Both values are compared with surrounding whitespace stripped. A bundle with at least one such Analysis is mapped. A recipe default of opengwasdb.column-map does not map a bundle whose every row names its own reader. A mapped bundle’s Build Recipe binds exactly one map, since files that need different maps belong to different Source Collections:

column_map:
  name: dbgap-phs002453-mvp-gia
  sha256: 3f0c...e9a1   # 64 lower-case hex characters
  file: dbgap-phs002453-mvp-gia.toml
Field Required Description
name Yes The map’s own name, as its TOML declares it. Any non-empty string, as OpenGWASDB accepts.
sha256 Yes The sha256 of the map file’s bytes, as 64 lower-case hex characters.
file Yes, except for a built-in The file the bundle carries the map in, under column_maps/. A file name, not a path: the Indexed Variant Subset grammar [A-Za-z0-9][A-Za-z0-9._-]{0,127} with no .., ending .toml.

name and sha256 are the fingerprint OpenGWASDB records in a mapped Resolution Record (resolution_config.column_map) and in a mapped Store’s manifest.json (provenance.column_map). The three can therefore be compared field for field. file is kept apart from name so that a map’s name never has to be a safe file name.

Built-in maps. OpenGWASDB ships two maps, gwas-ssf and finngen-r13. A binding with no file names one of them, and the bundle carries nothing for it, because the pinned OpenGWASDB package holds the bytes. Its sha256 records the built-in’s checksum as the Resolution Records report it. A binding with no file and any other name is refused. A carried copy of a built-in, bound with a file, is an ordinary carried map. A bundle whose rows use the dedicated readers opengwasdb.gwas-ssf or opengwasdb.finngen-r13 is not mapped and needs neither a binding nor a file. That covers every bundle registered before #292.

bundle.check() (_check_column_map) refuses, reporting every one it finds in one pass:

  • a mapped bundle whose Build Recipe binds no column_map;
  • a binding in a bundle that is not mapped: a map no Analysis reads through;
  • a bound file the bundle does not carry at column_maps/<file>, or one that is a symbolic link or not a regular file;
  • a carried map whose bytes do not hash to the bound sha256;
  • any other entry in column_maps/: a carried map that is not bound;
  • a column_maps that is a symbolic link or not a directory;
  • a malformed binding: not a mapping, null (omit the key to bind none), an unknown key, an empty name, a sha256 that is not 64 lower-case hex characters, a file outside the grammar, or no file with a name that is not a built-in;
  • column-map in build.options, complete.options or a variant_reference block’s options. The flag is composed from the checksummed binding, never passed through around it.

The contract checks a carried map shallowly. It must be UTF-8 TOML with a column_map_version and a name equal to the binding’s. Its full validation, covering fields, conventions and refusals, belongs to OpenGWASDB, which applies it at Analysis Resolution and at every build that reads through the map. The contract does not copy those rules.

A built-in binding’s sha256 must be that of the map file the pinned OpenGWASDB ships: bundle.check() takes the built-in names, and each file’s checksum, from opengwasdb.readers.column_map and refuses any other value, naming both.

The checksum contract. The binding’s name and sha256 are one value everywhere the map is used, and each use is checked against it:

  • Manifest Generation passes the resolver --column-map (a built-in’s name, or the release config’s column_map.path). Every mapped Resolution Record’s resolution_config.column_map must equal the binding, and the map’s checksum is part of the resolver’s settings digest and of the receipt’s resolution contract, so a changed map makes its Resolution Records stale: the resolver re-resolves them, and verify refuses records made under another map. The emitter writes the binding and copies a non-built-in map to column_maps/<file>.
  • Store Release Build passes --column-map to every build command that reads source files through it: build-dense-vcf, build-hybrid and the variant-reference pre-stage. A completion reads a Store and takes none; a command that takes no map (build-ragged-ssf) is refused for a bundle that binds one. A built-in goes by name. A carried map goes as a copy staged at <artifact root>/<store id>/work/column_maps/<file>, as the derived build manifest is, so the planned argv is the same from any checkout.
  • Before any build the release entry point, and the Snakefile’s onstart and column_map rule, re-hash column_maps/<file> against the binding and refuse a mismatch, naming the map. The staging rule re-hashes again as it copies. Snakemake treats an existing staged copy as up to date, so each step that lists it as an input checks the staged bytes against the binding immediately before it runs (resources.verify_staged_column_map), and a retried build whose staged copy changed is refused naming the map.
  • plan() is a pure function (ADR 0031): it reads only the binding’s recorded fields. That a built-in’s sha256 is the pinned package’s is check()’s to say.

assign-ancestry and estimate-phenotype-sd take no map yet (opengwasdb ADR 0063, opengwas/opengwasdb#285).

The passthrough rule

options keys are opengwasdb flag names. plan() renders key: value as --key value, booleans as bare flags (--key for true, --no-key for false), lists by repeating the flag, and never interprets a key. The registry does not know what --min-cor means and must not acquire a copy of opengwasdb’s parameter schema (ADR 0023).

An unrecognised or invalid flag fails in the CLI argument parser in milliseconds, before any expensive work. plan() composes only the arguments that are the registry’s own facts — store identity, the declared association_coverage for a Ragged build, the derived build manifest path, and artifact paths. Everything else comes from options.

A flag the registry composes is refused in options, because a recipe’s copy would be a second declaration: plan() refuses a build.options key that renders --association-coverage on a Ragged build, since release.yaml declares that value (ADR 0040) and a recipe change would be a new Store Release (ADR 0004).

validation.yaml

Release-level acceptance and build validation summary. This table is the one definition of the format; the workflow specification explains how register produces it rather than restating the fields. A measurement the build did not report is written as null — absence is recorded, never guessed or defaulted (issue #135).

Two writers produce this file at different times: - A Manifest Generator writes a candidate bundle’s record (Phase B): its acceptance checks, sidecar reports and warnings. - register writes the record of a built release (issue #119).

register replaces the candidate’s record; it does not merge with it. Its status, checks, warnings and errors hold only that run’s findings: the opengwasdb validate --format json verdict as checks.store, with that run’s warnings and errors exactly as validate printed them. None of them carries anything from the record being replaced (#195).

The candidate’s Phase B acceptance evidence is kept in its own labelled acceptance block, apart from those findings, and nothing in it feeds them (#195). register fills the block in one of three ways: - From a candidate record (one whose validator.name is not opengwasdb validate): every block it holds, verbatim – its checks, warnings and reports, and whatever evidence its generator records, such as reference_overlap (OGS-00011), store_composition (#203) or a dbGaP candidate’s own acceptance – except the fields that describe the generator’s run rather than the bundle: status, validated_at, validator, build_environment, observed and errors. The block is dated by the candidate’s own validated_at and tied to the commit that record came from. A candidate block named recorded_at or commit is refused, since it would overwrite that dating. - From a register-written record: its acceptance block is passed on verbatim, because the accepted bundle it describes is immutable. - Not at all, from a record #135 migrated (OGS-00001..7). Those records mix Phase B evidence with an earlier build’s findings, so nothing is extracted from them; git keeps them.

register names no generator’s evidence, so a generator that records a new kind is carried without changing register (#250).

A built or validated release must carry a validation.yaml whose status is one of not_run, passed, passed_with_warnings, or failed; bundle.check() rejects any other value. A validated release needs passed or passed_with_warnings: a passing opengwasdb validate is what makes a release validated, and its warnings are kept in the record (#195; see the workflow specification’s “The Release Status a Validation Record gives”). A candidate, accepted, superseded, or withdrawn release needs none.

A check’s stage is a precedence slot in the release policy: the policy settles an Analysis in a fixed order and, at each slot, the first failed exclusion check there decides. The slot fixes which reason wins when several apply and what the audit row carries: resolved (a successful Resolution Record, before Assigned Ancestry is read; the row carries none), ancestry_read (Assigned Ancestry read but not yet assessed; the row keeps the value read), selection (Assigned Ancestry tested against the Selection; the row carries it as af_assigned when it is a super-population code) and target_ancestry (the Analysis has the Selection’s ancestry, and its case-control counts when it needs them). Within a slot, registry order decides. A new check can use an existing slot without a policy change; a new slot is a change to the release policy.

A measurement an exclusion cannot use is never a silent pass. An invalid result where its check would decide membership stops the run; on an Analysis an earlier rule already excluded, it is only recorded. An Analysis that nothing excluded but that an exclusion check recorded as unmeasured (or invalid) is refused, naming the Analysis and the check, rather than included untested.

The INFO and MAF floors (defaults.info_score_threshold, defaults.maf_threshold) are not Quality Checks, because OpenGWASDB applies them to rows during Analysis Resolution and neither one decides an Analysis’s membership; their effect is measured by build_eligible_rows.

Contract. The sidecar is an optional Release Bundle contract file (ADR 0036: the contract grows per-Analysis Quality Check results). A bundle without it is valid; every bundle emitted before #285 has none. When it is present, bundle.check() (_check_quality_checks) requires:

  • the columns analysis_id, exclude_from_build, exclusion_reason, then one <check>, <check>_measured pair per check, at least one, with no check named twice;
  • one row per analyses.tsv Analysis, excluded audit rows included, in the same order, and no other row;
  • every <check> value in the result vocabulary above;
  • exclude_from_build exactly true or empty, agreeing with analyses.tsv; exclusion_reason non-empty exactly when excluded, and, when sidecars/exclusions.tsv is present, equal to its reason for that Analysis.

Store Release Build never reads it: membership is already decided in analyses.tsv (tests/packaging/test_boundary.py holds this).

Source connector files and freeze

A Source Collection plugs into Manifest Generation through files, never through code the pipeline calls (ADR 0036). Two of them meet at freeze (python3 -m manifest_generation.freeze, #283):

  • the Source Metadata Table: one row per intended Analysis in canonical columns – source_analysis_id (the only required one), Source Trait Label and ontology terms, Source Ancestry Label and super-population, study design, declared effect scale, sample size and case counts, genome build, Publication Metadata, licence, a provider grouping (store_key) and optional target columns for single-target Analyses;
  • the Acquisition Manifest: per Analysis, the file acquisition produced – location, size, sha256, source URL, metadata sidecar, lineage for a reformatted file – or the readiness status recording why there is none.

A release config’s Selection (all, an analyses list, or a where rule) picks the Analyses one release takes. Freeze reconciles them, fails on a selected Analysis with no manifest row, a row no Analysis claims or a duplicate, keeps an explained absence as a non-ready inventory row, and writes the Source Inventory with the selected connector rows frozen beside it.

docs/spec/source-connectors.md specifies every column, the vocabularies, the GWAS Catalog adapter and writer, the Selection grammar and the frozen inventory’s provenance.

Metadata resolvers

A metadata resolver is a small, independently callable module owned by one Source Collection (gwas-catalog-ssf, opengwas-gwas-vcf, …) that resolves the interpretation-bearing fields derive cannot safely infer from the raw summary-statistics file alone: stored_effect_scale, sample_size_kind, sample_size, n_cases, and n_controls. Resolvers read the provider’s own authoritative study/analysis metadata (a study table row, an API response, an endpoint manifest) — never the summary-statistics file itself, which may disagree with or omit this metadata (see issue #15’s ieu-a-7 example, where a GWAS-VCF ##SAMPLE header declares StudyType=Continuous for a study the source API correctly reports as case-control).

Conventionally, resolver modules live beside their provider, under src/manifest_generation/providers/<provider>/, one file per Source Collection, named for the resolved field set they share: resolve_<source_collection>_metadata(...).

Input is whatever raw metadata unit the provider exposes for one Analysis (free text, a parsed API record, …); shape is provider-specific and not part of this contract. Output is always a single resolved record with these fields:

Field Required Description
resolution_status Yes resolved or unresolved. Never a silent default — an Analysis whose metadata can’t be established gets an explicit unresolved record, not a defaulted value that looks plausible.
resolution_notes No Free-text reason when resolution_status = unresolved.
stored_effect_scale No Same controlled vocabulary as analyses.tsv: sd, log_or, or log_hazard. NA when resolution_status = unresolved.
sample_size_kind No Same controlled vocabulary as analyses.tsv: total, case_control, effective, or variant_level. NA when resolution_status = unresolved.
sample_size No Scalar study N. NA when resolution_status = unresolved.
n_cases No Case (or event) count. NA when not applicable (sample_size_kind != case_control) or unresolved.
n_controls No Control (or non-event) count. NA when not applicable or unresolved.

A caller (a derive stage, or a curation script such as ebi-studies.r) may adapt this generic record onto its own column names, but the resolver itself must not know which downstream shape it feeds — this is what lets derive stay agnostic to which provider it is talking to.

These implementations exist:

  • src/manifest_generation/providers/gwas_catalog/gwas_catalog_ssf.R (resolve_gwas_catalog_ssf_metadata()) resolves GWAS Catalog’s free-text “INITIAL SAMPLE SIZE” study field: a study whose parsed components include any cases/controls counts resolves as case_control with stored_effect_scale = log_or; otherwise it resolves as total with stored_effect_scale = sd; a field with no parseable numeric component resolves as unresolved.
  • src/manifest_generation/providers/ukb_b/provider_metadata.py (resolve_record(), issue #219), for the opengwas-gwas-vcf Source Collection, and the adapter that writes its Source Metadata Table (#289). It resolves a study’s ncase/ncontrol/sample_size from the OpenGWAS “gwasinfo” record – the provider JSON sidecar ukb-b ships beside each VCF, since the stored API token expired – rather than the source GWAS-VCF file’s ##SAMPLE header, which is not authoritative. A usable ncase/ncontrol pair resolves sample_size_kind as case_control; otherwise a usable sample_size resolves it as total; a record with neither resolves as unresolved. stored_effect_scale primarily follows the record’s units field (SD -> sd, log odds/logOR -> log_or, a hazard-ratio unit -> log_hazard), falling back to log_or/sd from ncase/ncontrol presence only when units is absent or unrecognised (issue #50: the ukb-b batch reports every trait on the SD scale, so inferring scale from case/control-count presence alone is wrong for that batch). The R resolver that held this contract (lib/metadata_resolvers/opengwas_api.R) retired with ukb-b’s R path (#289).
  • src/manifest_generation/providers/finngen/source_metadata_adapter.py (issue #288, docs/spec/source-connectors.md), FinnGen’s endpoint manifest, for the finngen-r13 Source Collection. It keeps the classification the collection’s retired R resolver applied: binary endpoint rows carry num_cases and num_controls and are case-control; FinnGen encodes its inverse-rank-normalised quantitative endpoints with category = Quantitative endpoints, the total N in num_cases, and num_controls = 0, and those rows are quantitative without misrepresenting that total as a case count. It refuses an endpoint it cannot describe honestly rather than leaving it unresolved; the release config’s method tiers turn study_design into stored_effect_scale/sample_size_kind.

Trait ontology mapping

Manifest Generation’s shared step (#286, ADR 0036 step 5). The Python pipeline maps every Analysis in src/manifest_generation/trait_ontology_mapping.py, after the resolver records are verified. It reads the source term from the Source Metadata Table’s source_trait_ontology_id/source_trait_ontology_label (GWAS Catalog’s MAPPED_TRAIT_URI/MAPPED_TRAIT) and the Source Trait Label. Precedence and methods are those below: - a source term is kept as source_provided; - otherwise an exact match of the trimmed, lower-cased Source Trait Label is canonical_table_lookup; - otherwise the Analysis is unmapped.

A source term is normalised to CURIEs term by term:

Source form CURIE
http://www.ebi.ac.uk/efo/EFO_0004839 EFO:0004839
http://purl.obolibrary.org/obo/MONDO_0005148 (any NS_local) MONDO:0005148
http://www.orpha.net/ORDO/Orphanet_101960 Orphanet:101960
a CURIE unchanged

Any other form is refused, naming the Analysis and the term: the run fails rather than emitting a URI or a guess. A comma-separated source list stays a list, its CURIEs joined by ", " in the source’s order, and the source label is kept verbatim (see trait_ontology_id above).

A source term is rejected using ogstores.bundle’s #141 guards when: - any term is gene- or protein-shaped, checked both before and after normalisation, so a PURL HGNC_1234 is caught as HGNC:1234; - or its label, taken whole, is an identifier-authority name.

A rejected term falls through to the table, and the rejection and its reason are recorded. A source term with no label is kept as source_provided, and the run counts how many there are.

The table is read from resources/reference-resources/canonical-trait-mapping-efo/, a directory named explicitly: no network is involved. Its resource.yaml location is resolved against that directory: the declared file must be in the resource’s own directory, and a declared location_kind must be tracked_file. A malformed curated row fails the load, and the refusal lists up to twenty problems and counts the rest: - a blank lookup value; - a non-CURIE term; - a gene-shaped term or an authority-name label; - a label listed twice.

The table’s identity, the method counts, the count of source terms without a label, and the rejected source terms are recorded in validation.yaml’s trait_ontology_mapping block.

The lookup lives in this registry rather than in OpenGWASDB ADR 0021. A source-provided term is kept even when the ontology has deprecated it, and is recorded as source_provided; a plausible-looking invented replacement would be worse than the genuine obsolete term.

Quality Check configuration

A generator config’s optional top-level quality_checks block overrides a Quality Check’s shared default threshold for one release (#285):

quality_checks:
  build_eligible_rows: 1000   # exclude an Analysis with fewer build-eligible rows

Each key names a registered check that has a threshold; its value is parsed by that check (build_eligible_rows takes a whole number of rows of at least 1). An unknown name, a check with no threshold (one that tests a status), or a value the check refuses is a config error. A check’s kind is part of its declaration and cannot be overridden.

Thresholds are recorded twice. validation.yaml quality_checks.<check> carries the effective and default thresholds and whether this release overrode it. The resolution receipt’s contract always carries a quality_checks entry holding the effective thresholds, defaults included, and the release’s overrides, so changing an override or a shared default makes the receipt stale and verify/emit refuse it until resolution is re-run. A receipt written before #285 has no such entry and is stale for the same reason.

QC panel configuration

The shared pipeline keeps the QC panel in every region-filtered file: a release config’s region_policy.qc_panel_resource_id names it, and acquisition records the panel’s identity in each file’s lineage (#300, release config). The R generators’ filter.qc_panel block, described below for the bundles they emitted, retired with them.

A generator config’s filter.qc_panel block configured unconditional retention of the fixed QC variant panel (issue #28/#29/#30) for one release. Unlike the signal-driven sparse regions (cis/significant_trans/suggestive_trans), the QC panel is retained regardless of an Analysis’s p_value distribution, so ancestry assignment and reference-AF effect-scale validation have a stable variant backbone even for Analyses with few or no genome-wide-significant hits:

Field Required Description
enabled Yes Whether this release retains the QC panel in every Analysis’s filtered file.
resource_id Yes when enabled resource_id of the declared kind: qc_panel Reference Resource to retain (see “Reference Resource declaration”).

QC-panel retention is purely additive: a release that does not configure filter.qc_panel behaves exactly as before, and enabling it for one release never changes another’s filtered output. Retained QC-panel rows are recorded in the sparse-region sidecar with region_kind: qc_panel (one row per chromosome the panel actually matched in that Analysis’s source file, spanning the matched positions), distinct from the signal-driven region kinds, and sidecars/filter_summary.tsv gets a qc_panel_rows count per Analysis (0 for releases that do not configure a panel).

Effect-scale validation (issue #16) and ancestry assignment (issue #23/#25) deliberately do not distinguish QC-panel rows from signal-driven rows when choosing which retained variants to use for AF/SD computations — both continue to consume every retained row with usable allele-frequency data uniformly. Retaining the QC panel already directly grows that pool for low-power Analyses; preferring QC-panel rows exclusively would need to discard perfectly good signal-driven rows for well-powered Analyses, for no demonstrated ascertainment benefit. This can be revisited if evidence of an ascertainment problem emerges, but is not assumed by default.

Acceptance rule of thumb

A release bundle is acceptable when analyses.tsv is enough for OpenGWASDB to build the intended store, release.yaml and build.yaml are enough to explain what the store is and how to rebuild it, and sidecars are enough to audit any non-obvious derived metadata without blocking low-effort source ingestion. Run pixi run bundle-check to confirm it.
