Epic #232 execution record

Scope authority: epic #232, the revised approved scope of #216. This record describes implementation and integration evidence, not qualification of the full release matrix.

Current integration checkpoint — 12 October 2026 UTC

The owner authorised review, conflict resolution and PR merges to dev after another orchestration session advanced the work. This supersedes the initial no-merge instruction; it does not accept scientific candidates or authorise production builds, conversions, completion, validation or publication.

Execution and review gates

  1. Reconcile exact intended, manifest, admitted, excluded and actually built membership. Missing, duplicate, truncated or mismatched files fail loudly.
  2. Explicit human acceptance freezes the Release Manifest Candidate. Material membership/recipe choices require a new immutable identity and lineage.
  3. Verify the pinned runtime, required capabilities, format-compatible parent and ancestry-/assembly-matched Reference Resources before writes.
  4. The existing Phase A pixi run release interface owns locking, recovery and execution. No direct Snakemake bypass or registry-side association processing.
  5. Every full release ticket includes its scientific checks, applicable required Ragged/Overflow variant indexes and optional Dense-component HM3, exhaustive validation, genuine warnings and registration receipts. Fixture tests are not full-scale qualification evidence.
  6. Code-review GO and code merge are not scientific acceptance or permission to replace published Stores. Preserve historical artifacts and valid checkpoints.

Resource envelope

  • Lightweight tests: at most four CPUs per worker, BLAS threads one.
  • Bulk source scans: one coordinated slot, at most two readers. #219’s completed source verification released that slot; no new bulk scan is authorised here.
  • #220 may inspect mapping tables and named metadata/header probes; no recursive multi-TB content scans or automatic downloads/conversions.
  • Full release execution needs its own acceptance gate and resource allocation.
  • No recursive delegation; each ticket has a DeepSeek Flash worker and separate Gemini 3.8 Flash reviewer in an isolated ticket worktree/Herdr tab. Session handles are ephemeral operator state, not release provenance.
