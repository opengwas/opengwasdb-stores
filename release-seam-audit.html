Release seam audit

Historical record. This audit was written on 2026-09-10 and is kept as written. Its relative links into the family-first bundle archive are dead: that directory was retired in #252, and each bundle it held is now registered in stores/<store-id>/ or retired with git history keeping it.

Research for Audit the existing release seam decisions and working-store evidence, against repository commit 8bd722b on 2026-09-10. The seed is The release seam to opengwasdb has no interface: builder.entrypoint is inert, the Builder Manifest adapter is copy-pasted and lossy, and the bundle format has no owner module.

Answer

The seed’s central diagnosis stands: this repository has working pieces for several source/layout combinations, but no release-centric interface joins them into one observable, resumable route from an acquired Source Inventory to a validated Release Artifact. Four of its five directions remain live, with two important corrections:

  1. The release seam is still inert, but its boundary is already decided. All 20 committed build.yaml files declare builder.entrypoint, but no runtime code reads that field. Instead, three standalone build wrappers and the BESD generator import OpenGWASDB builders directly; Reference Completion and rho construction recorded in committed releases were run manually through the OpenGWASDB CLI. The seed is wrong that all four paths use “the same import”: Dense, Hybrid, Ragged SSF and BESD have distinct call shapes. The missing work is therefore not another repository-boundary decision or a naive dynamic import. opengwasdb-stores <-> opengwasdb interface and script placement already decided that the Release Bundle is the handoff, this repository owns orchestration, and OpenGWASDB owns readers and builders. Unify repository software management with Pixi also already selected pixi run <task> as the operator interface. The later design must implement those decisions.
  2. The Builder Manifest adapter is still duplicated and the Hybrid path is still lossy. The Dense wrapper translates and passes the interpretation-bearing fields at write_builder_manifest, and its FinnGen end-to-end test verifies their read-back from a real built fixture (test). The Hybrid wrapper has a separate, shorter map that omits sample_size_kind, sample_size_scope, n_cases, n_controls, original_effect_scale, ancestry_assignment_method, and all ancestry_prop_* fields (Hybrid adapter). Its read-back then asks for several of the omitted fields (Hybrid checks), and both Hybrid Trial Store Releases record the resulting omissions (case-control validation, quantitative validation). The old upstream defect is fixed: Dense/Hybrid VCF-manifest builders drop n_cases/n_controls/sample_size_kind/sample_size_scope/original_effect_scale, and fabricate ancestry_assignment_method confirms the current builder accepts all six fixed fields. A current rebuild loses them because the local Hybrid adapter never supplies them. The seed also overstates the test gap: Dense translation is integration-tested, although neither adapter has a focused contract test and Hybrid has no corresponding build test.
  3. The Release Bundle still has no owner module, but analyses.tsv is no longer merely prose. release_yaml.py remains a custom subset parser plus validation merger, while five generator implementations write the bundle independently. The R Ragged and Hybrid generators also retain separate validation-merge implementations (Ragged, Hybrid). However, the seed’s claim that the schema is “enforced by nothing” is superseded by Schema-conformance check against an opengwasdb-owned schema: the current bridge delegates analyses.tsv validation to opengwasdb.model.analyses (implementation) and tests both failures and real bundles (tests). A Release Bundle owner must compose, not duplicate, OpenGWASDB’s shared Analysis schema and must additionally own registry-specific structure, I/O, state transitions, and validation merging.
  4. The naming collision is real; the proposed directory layout is not yet a decision. families/<family>/generators/ contains the family-specific configuration and thin shims that match the domain definition of Manifest Generator, while resources/generators/<source-format>-<layout>/ also contains shared selection, download/filter, annotation, building, and validation code. The latter names conflate Source Format, Store Layout, and several phases. Family-first external artifact layout settles durable artifact paths only, so applying the same rule to source-code layout would be a new design choice. store_key is likewise absent from CONTEXT.md, yet is used as candidate-grouping data, written into some release.yaml files, used as a physical store name, and sometimes substituted for OpenGWASDB’s store_id (Ragged build). Its candidate-pool role must be distinguished from Store Release identity; it should not become a fourth authoritative identifier by accident.
  5. Release identity and lineage should not be reopened. Store release identity, Family-scoped release IDs, and Reference completion as release lineage already establish immutable releases, the (Store Family ID, Family Release ID) identity pair, source-natural family-scoped IDs, and Reference-Completed releases linked to their observed-only parents. Contrary to the seed, the ukb-b resolved and completed bundles do populate lineage.derived_from (resolved, completed). Existing IDs do redundantly encode layout, completion, and even an issue reference, but they are immutable historical identifiers. Preserve them; enforce the existing source-natural convention for future releases rather than inventing a new identity scheme.

What is already settled

Later design tickets should treat the following as constraints, not open questions.

Concern Existing decision Consequence for the workflow
Repository boundary Store registry boundary, Manifest generators own orchestration only This repository orchestrates and records releases. Reusable source readers, normalisation, statistical logic, storage builders, and query behavior remain in OpenGWASDB.
Source model Source formats and reader capabilities, Single-source store families, Reference resources are build resources One Store Family consumes one homogeneous Source Collection; reader capability and Reference Resources are explicit inputs, not branches inferred from paths.
Handoff shape Custom manifest generators with standard release manifests, Separate release manifests from build recipes, YAML metadata and TSV tables, Release manifest bundles Preserve the four-file Release Bundle, the separation of accepted membership from Build Recipe, and YAML/TSV conventions. A module may own the format without collapsing it into one file.
Metadata authority OpenGWASDB owns the shared analysis schema, Trait Ontology Mapping lookup lives in the registry, not OpenGWASDB Validate shared Analysis fields against OpenGWASDB; keep registry provenance fields and the deliberate ontology-lookup exception here. The adapter must be lossless across this seam.
Existing manifest phases Metadata pipeline for ragged release manifests, docs/release-metadata-schema.md discover -> select -> derive -> emit -> accept is existing language. A larger execution workflow should contain or map these stages explicitly, not silently redefine them.
Release and artifact identity Store release identity, Family-scoped release IDs, Reference completion as release lineage, Family-first external artifact layout Material manifest/build changes and Reference Completion produce immutable lineage-linked Store Releases; durable paths use Family and Family Release identity.
Storage boundary Registry not artifact store Keep source data, stores, checkpoints, and large logs outside Git; retain small manifests, summaries, and report pointers here.
Publication boundary Registry and service catalogue boundary Building and validating can end at the Release Artifact. Activation, routing, and default served releases belong elsewhere.
Environment Unify repository software management with Pixi, pixi.toml Keep one Pixi-fronted operator interface and an immutable OpenGWASDB pin; do not add a competing user-facing environment/runner interface.

The current Release Status vocabulary is a registry lifecycle (candidate, accepted, built, validated, superseded, withdrawn), not execution state (domain definition). A resumable workflow therefore needs a separate phase/checkpoint record; repurposing release.yaml.status as scheduler state would contradict the domain model.

Working-store evidence

The exact seven-store development set is enumerated by Rebuild all pilot stores on current main and stress-test the new encodings. It is a useful coverage matrix, but these are evidence fixtures rather than seven implementations to preserve.

Trial Store Release Distinct coverage Evidence and seam exposed
eqtlgen-cis-pilot/pilot-10 BESD -> Ragged, cis, shared multi-Analysis source bundle The generator performs selection, build, read-back, report writing, and bundle emission in one Python program; it does not expose the staged interface used by other families.
eqtlgen-cis-pilot/pilot-10-completed BESD -> Ragged Reference-Completed Completion uses a different OpenGWASDB API and was invoked manually. The first rebuild used the wrong Analysis IDs because tissue was an implicit generator argument, then had to be redone; that is direct evidence of operator-only invocation knowledge (rebuild record).

This ten-Analysis slice was explicitly created as an independent end-to-end proof rather than a replacement for the 100-Analysis release (release evidence), making it the appropriate fast workflow fixture. The catalogue separately records artifact-path drift and a legacy schema in the 100-Analysis predecessor (catalogue).

This matrix spans three Store Layouts, four input shapes/capabilities, single-file-per-Analysis and shared bundles, cis and no-cis Ragged policies, observed-only and lineage-linked completion examples, and both successful and deliberately adverse validation outcomes. It also shows inconsistent report contracts: validation.yaml.reports ranges from empty to selection, downloads, derivations, ancestry, SD, filter, build, and narrative assessment reports, with different stage combinations per family. A common envelope should require phase identity, inputs, outputs, tool/environment provenance, status, timings/resource use, checks, warnings/errors, and pointers while allowing layout-specific payloads.

All seven were rebuilt successfully as format 2.0, but outside the curated release paths, while the repository remained pinned to an older OpenGWASDB revision (rebuild record, storage follow-up). The same rebuild exposed GCST002047 is stored with z uncorrelated with its own p-values: its source beta column is odds ratios: both old and rebuilt stores passed structural validation despite an entire Analysis being scientifically nonsensical. The Preflight Review Gate and scientific reports are therefore essential; validate_store alone is not an acceptance decision.

All committed catalogue stores were built using OpenGWASDB format 0.1; Store format 1.0: z is int16 fixed point, and the manifest declares its encoding (opengwasdb#114) records that they remain readable but require rebuilding for the newer format (catalogue warning). Trial coverage should therefore be asserted through reproducible behavior and reports, not byte-for-byte preservation of old artifacts.

Full-scale and current-server evidence

The committed ukb-b/dense-observed-vcf-c128-completed-issue34 release is the original scale proof: 2,514 Analyses, 11.19 million variants, 11.27 billion imputed cells, a 71 GB completed store, and about 7.7 hours for Reference Completion (release evidence, catalogue). It was produced with a manual opengwasdb complete-dense command and formally registered later, including an in-place schema migration. This validates OpenGWASDB’s engine, but demonstrates that operator memory and retrospective bookkeeping still bridge the release seam.

Newer tracker evidence is even stronger. Verify ukb-b at genome scale: build and migration under format 3.0 records a fresh 2,511-Analysis by 9,847,701-variant build taking 13 hours 30 minutes; its measurement report records 424.84 GB of input, a 41.66 GB format 3.0 store, and an 11-hour-35-minute format 2.0 baseline. Its Reference-Completed sibling adds roughly 7 hours over 1,357 LD blocks. These are authoritative current-server scale measurements, not projections.

Additional uncommitted operator-worktree evidence was inspected read-only on 2026-09-10:

  • families/ukb-b/releases/dense-observed-vcf-c128-rebuild117/sidecars/build_report.tsv records a current Dense rebuild of 2,511 buildable Analyses from 424.8 GB of source data to a 42.6 GB store in 48,607.7 seconds (about 13.5 hours), with store validation passing.
  • /data/opengwasdb/raw/ contains 17,300 files totalling about 2.35 TB, including the mass GWAS Catalog download in progress.
  • .rebuild133/ contains fresh runs overlapping the development matrix plus the ukb-b Dense trial, but the operator invoked them through family/layout-specific paths and collected them manually.

These local observations are not committed evidence and should not be promoted into registry truth as-is. They do confirm the operational requirements: completion markers must survive multi-hour phases; a rerun must distinguish reusable outputs from partial/corrupt ones; source acquisition must finish and produce a verifiable Source Inventory before the main workflow starts; and reports/checkpoints must be discoverable without reconstructing commands from shell history.

Constraints for the remaining design

  1. Start from an acquired, verified Source Inventory. Repository-owned Source Acquisition Helpers are valuable, and FinnGen already proves resumable download mechanics, but they should terminate at a common inventory contract. The main workflow starts there. Today the GWAS Catalog Source Collection declares inventory: null, and the OpenGWAS inventory is only a header (source collections); this handoff is not yet implemented.
  2. Use one release-centric operator command. It should select the family/release, validate configuration and inventory, run or resume explicit phases, expose the single Preflight Review Gate, and stop at a validated Release Artifact. Pixi fronts that command; a workflow engine may implement it.
  3. Treat builder.entrypoint as typed dispatch, not arbitrary dynamic import. Current builder APIs have different signatures and require registry-side translation, Reference Resources, validation, and report handling. The design must decide whether the manifest names a supported adapter/capability or an OpenGWASDB callable, but the runner must fail closed on unsupported combinations and always preserve the standard read-back/validation contract.
  4. Make adapter ownership singular and lossless. One tested seam should transform the accepted registry Analysis rows into whatever an OpenGWASDB builder requires. Per-layout differences should be explicit data or implementations behind that seam, not divergent copies. Test the exact shared-core and registry-to-builder column contract for Dense, Hybrid, Ragged, and BESD.
  5. Give the Release Bundle one owner without stealing OpenGWASDB’s schema. Centralise reading, writing, registry-specific structural validation, status transitions, and cumulative validation/report merging. Continue delegating the shared analyses.tsv contract to OpenGWASDB.
  6. Separate lifecycle, execution, and approval state. release.yaml.status, per-phase completion/checkpoints, and the one human Preflight approval are different facts. Record each explicitly, with input/config/code/environment fingerprints so “complete” means safely reusable.
  7. Model expensive build and derived work as phases with declared dependencies. The phase model must place build, read-back validation, top-hit construction, rho construction where applicable, and final artifact validation, with visible reports and useful restart boundaries. Reference Completion remains a separate derived Store Release connected through Release Lineage, not an in-place phase that mutates its observed-only parent.
  8. Standardise the report envelope, not every report body. The Trial Store Releases prove that source/layout-specific evidence is necessary. Require consistent phase status, provenance, metrics, checks and artifact pointers, then allow ancestry, SD, sparse-region, Hybrid partition, top-hit and rho-specific schemas beneath it.
  9. Preserve historical release IDs and migrate incrementally. Existing bundles and family commands should be adoptable behind adapters while the common workflow is introduced. Do not rename published IDs, rewrite old store artifacts, or make the outdated 0.1 binaries the conformance oracle.
  10. Keep the scoped exclusions firm. No multi-store queue, HPC/cloud abstraction, publishing/activation, or storage/query redesign is needed to close this seam.

Bottom line

The route should build on the seed rather than restart it: implement the already-decided Release Bundle handoff and Pixi interface; centralise Release Bundle and adapter ownership; preserve existing domain, identity, and repository boundaries; and add a separate resumable phase/evidence model proven across the seven Trial Store Releases and the full-scale ukb-b case. The only seed proposal that should not become a fresh design debate is Release identity/lineage—the ADRs already answer it. The schema claim also needs narrowing: shared Analysis validation exists; bundle-level ownership does not.
