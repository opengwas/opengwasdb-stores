Store Audit

The specification of the read-only Store Audit commands (stores #372 and #373, epic #371). It follows ADR 0023 (the seam is a command line) and leaves source reading, Store access and format semantics with opengwasdb (ADRs 0012 and 0017). The words are CONTEXT.md’s. This file is the contract: the commands, what they read, what their reports say, and how a reader is meant to act on them.

Two commands share one module and one read-only discipline:

  • reconcile (#372) reconciles the Store’s axis – the shared variant axis, its Dense Component and the off-panel remainder – against what the Store records.
  • attribute (#373) attributes the off-panel union to the Analyses and publications that observe it, and pins a seeded sample for the raw-row trace (#374).
  • trace (#374) follows that sample back to the raw source rows, the frequency each source reports, and the admission decision the builder made for each of them.

reconcile never reads the Ragged body’s variant indices, attribute never reconciles a count it did not measure, and trace never decides an admission of its own: it replays opengwasdb.build.row_admission.admit_rows under the Analysis’s declared policies and reports what that rule did. A reader who wants “how big is the off-panel part” reads reconcile; “whose is it” reads attribute; “why was it admitted” reads trace.

The command

python3 -m ogstores.audit reconcile <store_path> --output <evidence_json>
pixi run audit-store reconcile /data/opengwasdb/stores/OGS-00011/store.opengwasdb \
  --output /data/opengwasdb/work/epic371/orchestrate/opengwasdb-stores-371/evidence/372/reconciliation.json
Option Meaning
--reference PATH reconcile the off-panel partition against this construction variant reference instead of the one the Store records
--skip-reference do not reconcile against a reference at all. Recorded as skipped, removed from scope.measured, added to scope.not_measured, and the run reports ok: false (exit 1). Refused together with --reference
--no-identities skip the variant-table pass (duplicate ALIDs, multiallelics, reference membership). Recorded as scanned: false, with the same ok: false consequence
--band-variants N axis entries one band of the occupancy scan spans (default 4,000,000). The answer does not depend on it
--verify auto\|sha256\|metadata how the Store is proved unchanged: sha256 every file, size+mtime_ns only, or auto (sha256 up to 512 MiB) 
python3 -m ogstores.audit attribute <store_path> --output <evidence_json> \
  [--sample-output <sample_tsv>]
pixi run audit-store attribute /data/opengwasdb/stores/OGS-00011/store.opengwasdb \
  --output /data/opengwasdb/work/epic371/orchestrate/opengwasdb-stores-371/evidence/373/attribution.json \
  --sample-output /data/opengwasdb/work/epic371/orchestrate/opengwasdb-stores-371/evidence/373/sample.tsv
Option Meaning
--sample-output PATH write the seeded, stratified sample TSV here; must be outside the Store. Omitted, no sample is written, sample.written is false and the stage is named in scope.skipped
--seed N the seed every sample choice derives from (default 42). The report’s counts do not depend on it
--top N how many leading contributors the sample draws exclusive variants from, and how deep the union-share measurement goes (default 5)
--sample-per-stratum N rows each stratum keeps (default 20). Each stratum holds 8N candidates before the allele-class round-robin picks
--band-variants N axis entries one band of the attribution and sample scans spans (default 8,000,000). The answer does not depend on it
--band-rows N association rows one band of the support scan spans (default 16,000,000, 64 MB of int32). The answer does not depend on it
--verify auto\|sha256\|metadata as reconcile 
python3 -m ogstores.audit trace <store_path> --sample <sample_tsv> \
  --manifest <build_analyses_tsv> --output <evidence_json>
pixi run audit-store trace /data/opengwasdb/stores/OGS-00011/store.opengwasdb \
  --sample /data/opengwasdb/work/epic371/orchestrate/opengwasdb-stores-371/evidence/373/sample.tsv \
  --manifest /data/opengwasdb/stores/OGS-00011/work/analyses.tsv \
  --output /data/opengwasdb/work/epic371/orchestrate/opengwasdb-stores-371/evidence/374/trace.json
Option Meaning
--sample PATH the sample TSV attribute --sample-output wrote. Must be outside the Store
--manifest PATH the build manifest the Store was built from. Its source_file/source_url is the only record of which raw file each Analysis was read from, and its maf_threshold/info_score_threshold columns are the policies replayed. The Store’s own analyses.tsv is Analytical Metadata and deliberately carries neither
--raw-root PATH where a manifest source_url is expected to land locally when its source_file is gone (default /data/opengwasdb/raw/ebi-gwas-catalog)
--limit N trace at most N sample rows. A limited run reports the rows it read and never pretends to close the sample
--workers N source files scanned in parallel (default min(8, cores)). Each file is read exactly once whatever the sample draws from it, so this is files in flight, not a per-row optimisation
--verify auto\|sha256\|metadata as reconcile

Exit codes:

Code Meaning
0 reconciled, and ok is true: every disagreement is a finding
1 reconciled, and ok is false: an error (the Store’s artifact and its own record disagree, or evidence the audit requires is missing or contradicts itself), or a stage the caller explicitly skipped
2 the Store cannot be audited at all: no manifest, not a hybrid Store, a required artifact absent, a bad invocation

A 2 is never a report about the Store, and a 1 is never a pass. ok is the exit code: it is true exactly when no error-severity inconsistency was recorded, and skipping a stage is one of those – a run that did not measure a required partition must not be read as an exact, closed reconciliation. The command exits 2 rather than writing a report that reconciles something other than the Store the caller named, and refuses an --output inside the Store.

Scope

One slice, and deliberately not more: reconcile reconciles the axis, not its causes. It reads the Store Release’s own artifact and its own record – manifest.json, variants.tsv.gz and its ALID search index, data.zarr’s ragged/offsets, ragged/variant_index lengths and ragged/by_variant/offsets, dense/dense_to_shared.npy, analyses.tsv, and records/build.json beside it – and the construction reference the record names. It never reads a Build Recipe, so a Store whose recipe has moved on is still audited as built.

What it does not measure is in the report’s scope.not_measured, with the ticket that owns each: per-Analysis and per-publication attribution and support across Analyses (both measured by attribute, below), source frequency evidence (#374), and rsid groups (#375). Their absence is stated, not left to be inferred from a report that has no field for them.

attribute is the other half of the same slice: it names the contributors and stops at the Store’s edge. It does not read a source file, so it cannot say whether an association should have been admitted – only that a given Analysis contributed it, and which raw row of that Analysis’s source it came from. That is #374’s question, and the sample below is what makes it askable; trace answers it, from the source files outwards.

Prerequisites, and what makes them an error

The Store’s own evidence is required, not optional. Each of these is an error-severity inconsistency, so the run reports ok: false and exits 1 rather than passing with a blank where a fact should be:

Missing or contradicted Kind
records/build.json absent build_record_unavailable
records/build.json unreadable, or not a JSON object build_record_unreadable
records/build.json with no opengwasdb_rev build_revision_unrecorded
analyses.tsv absent analyses_tsv_unavailable
analyses.tsv undecodable analyses_tsv_unavailable
provenance missing any of n_variants, n_analyses, n_panel, n_off_panel, n_overflow_associations, ragged.by_variant.n_axis, ragged.by_variant.n_rows recorded_counts_incomplete
any of those counts disagreeing with the artifact recorded_*_disagrees
an ALID search index whose two arrays differ in length alid_index_half_written
an ALID search index that is not sorted alid_index_not_sorted
an ALID search index whose entry count differs from the table’s indexable rows alid_index_disagrees_with_table
a sampled row whose ALID contradicts its own chromosome, position or allele columns alid_sample_mismatch
a Dense-axis variant carrying Overflow associations (disjoint partition) dense_axis_rows_carry_overflow_associations
a Store directory replaced or removed during the audit store_replaced_during_audit, store_vanished_during_audit
a release lock taken while the audit was reading the Store release_started_during_audit
any file in the Store whose size, mtime or hash changed store_modified
a stage the caller skipped skipped_evidence

The ALID cross-check is a Store-level check and does not replace opengwasdb’s variant normalisation (ADR 0017): it asks whether a stored row’s alid string agrees with that row’s own columns, not whether the identity the builder derived from a source row was the right one – that is the engine’s, and a change to it is the engine’s change (ADR 0023’s seam is a command line, and this command consumes it). Its sample is every 100,000th row, recorded as identities.alid_consistency_sample with the stride, so a reader knows the check’s power rather than inferring a census from it.

A stable, read-only view

A Reference Completion replaces a Store under its own id (ADR 0037), so the thing an audit describes has to be one directory and not two. Two independent guards, both recorded in store.stable_view:

  • the Store directory’s device and inode (and its parent’s) before and after – a rename swap changes them, and the report then carries store_replaced_during_audit;
  • the release lock (ogstores.release.lock_holder, a non-blocking shared flock on <artifact-root>/.release-locks/<store_id>.lock), probed at the start and at the end. A lock held throughout is a finding (release_lock_held) because a long-lived orchestrator can hold one without touching this Store; a lock taken during the audit is an error. The probe creates and removes nothing, so asking cannot change the release.

What it reconciles

Fact Read from Reconciled against
shared-axis length VariantAxis over variants.tsv.gz recorded provenance.n_variants, table row count
Dense-axis length dense/dense_to_shared.npy, the Dense Component’s own axis recorded provenance.hybrid.n_panel
off-panel length axis minus the distinct mapped rows recorded provenance.hybrid.n_off_panel
observed occupancy ragged/by_variant/offsets in bands: counts = diff(offsets[lo:hi+1]) the Analysis-major ragged/offsets, the recorded n_overflow_associations
variant-major index span ByVariantReader (spans the axis, not stale against the component) recorded provenance.ragged.by_variant
Analyses ragged/offsets entries minus one analyses.tsv rows, recorded n_analyses
canonical identity every variants.tsv.gz row, plus the sorted ALID search index the axis: one row per canonical ALID
construction reference read_variant_reference on the recorded path the axis, and the Dense Component’s row set

Canonical identity is counted twice on purpose. The table streaming pass counts duplicates only among rows sharing a position – the axis is position-ordered – while the sorted ALID search index counts them exactly, with no ordering assumption, by counting adjacent equal entries. The rows whose ALID is wider than the index’s fixed 32-byte key are counted from the table instead, because the index leaves them out (opengwasdb issue #127). Two counts that agree are the evidence that either is right.

The construction reference is recorded by identity (path, size, mtime, sha256, ALID count) because a panel that moves cannot be reconciled with afterwards. role states which reference it is: the build’s own construction panel, not the LD panel a Reference Completion uses (ADR 0037).

What attribute attributes

Four questions, each answered exactly, from the Store’s own arrays:

Question Read from Reported as
how many distinct Analyses observe each off-panel entry each Analysis’s row range of ragged/variant_index, streamed in bands support.analyses, bucketed 1, 2, 3-10, 11-100, 101+
how many distinct publications observe it the same rows, coded to publications through analyses.tsv support.publications
is it observed by exactly one Analysis, or by Analyses of exactly one publication the same two planes support.exclusive_to_one_analysis_variants, support.exclusive_to_one_publication_variants, and ..._multi_analysis_variants for the publication-only case that several Analyses share
whose it is, how much each holds, and how much of the union the leaders explain the planes per axis band, then exact unions of the leading contributors’ own variant lists contributors.analyses, contributors.publications, concentration; the full tables are evidence/373/analyses.tsv and evidence/373/publications.tsv

The support plane is two uint16 arrays over the axis (distinct Analyses, distinct publications) plus their two observer planes and two deduplication stamps – 1.4 GB on OGS-00011’s 114,514,113-entry axis, and the scan never holds the 2.9B-row body: one band of ragged/variant_index at a time.

Two details are load-bearing rather than tidy, and the suite pins each:

  • Analyses are visited in publication order, not index order, and each block is deduplicated within itself before the stamps are consulted. A stamp means “already counted for this publication”, so a publication’s Analyses must be contiguous: in index order an Analysis of publication B can stamp an entry between two Analyses of publication A, and A’s second Analysis then counts it twice. And two rows for one variant inside one band are two stamps that both read as new, so the block is np.uniqued first.
  • Consequences are reported rather than hidden. repeated_variant_rows_in_one_analysis and analysis_variant_lists_not_increasing are findings, and single_observer_variants_carry_several_associations is a finding too: an exclusive variant count and an exclusive association count are kept apart and both reported, so a Store that repeats a row cannot make one stand in for the other.

A publication is analyses.tsv’s publication_pmid, or its publication_doi when no pmid is recorded. An Analysis with neither is retained as its own explicitly unknown group (publication_key_kind: "unknown", key unknown:<analysis_id>, reported by the publication_metadata_unknown finding): unknowns are neither dropped nor coalesced, because one merged “unknown” would report two unrelated Analyses as one publication’s. One publication recorded with two DOIs or two first authors (publication_metadata_ambiguous) is an error: attribution that guessed between two publications would be a wrong answer that looks like a right one.

All metadata is indexed by analysis_index, never by analyses.tsv row order, and the file’s own numbering is checked against the axis (analysis_index_disagrees_with_position, an error, and a 2 when the numbering cannot be read against the Ragged partition at all).

concentration is the epic’s question about attribution rather than a sum. Each leading contributor’s variant list is unioned exactly in one boolean plane over the axis, and top_analyses/top_publications report the union at prefixes 1, 2, 5, 10 and the last contributor, plus its share of census.attributed_union_variants. A share is never the sum of the contributors’ counts: two Analyses of one publication share most of their variants, and the report says "numerator": "distinct off-panel variants of the prefix's union, not the sum of theirs".

allele_classes and chromosomes come from one stream of the Store Variant Table, off-panel rows only, classified snp (one base against one base), indel (alleles of different lengths) or complex (two equal-length alleles longer than one base). A position’s row group is counted separately (multiallelic_positions, rows_at_multiallelic_positions) so a site’s row count is never confused with a row’s class.

census reconciles the attributed union against the two accounts of its size: the axis minus the Dense Component, and the n_off_panel the Store records. attributed_union_variants counts off-panel entries at least one Analysis observes. On OGS-00011 all three agree at 101,098,177.

The sample

--sample-output writes a TSV whose rows are starting points for #374’s raw-row trace, not a statistical estimate: every count in the report is a census, and the sample exists only to name rows.

Column Meaning
sample_id S00000-style id, assigned after sorting by stratum, variant and Analysis
analysis_id, analysis_index, publication_pmid the Analysis the row is attributed to, and its publication. Every row names one: a row a trace cannot attribute is not a starting point
alid, rsid the variant’s canonical identity and its rsid (empty when the table records none)
stratum which question selected the row (below)
on_panel True for a Dense-axis control, False for an off-panel row
source_row_lookup_hint where the row is, exactly (below)
allele_class, chromosome, variant_index context a trace needs without a second query
n_analyses, n_publications how many distinct Analyses and publications observe the variant

The strata are the ticket’s questions:

Stratum Rows drawn from
exclusive_analysis:<analysis_index> entries observed by exactly that Analysis, for the leading contributors by exclusive variants
exclusive_publication:<publication_key> entries observed by several Analyses of exactly that publication, for the leading publications by exclusive variants
shared_multi_publication entries observed by two or more publications
random_off_panel the whole attributed union
on_panel_control Dense-axis entries

Determinism. A candidate’s rank is a SplitMix64 hash of its axis index mixed with --seed, so the choice is a property of the seed and the Store. Each stratum keeps its 8N smallest hashes (N = --sample-per-stratum), then takes N of them round-robin over the allele classes, smallest hash first – round-robin so that a rare class (7.8M indels against 93.3M SNPs on OGS-00011) still reaches the sample. Band size, iteration order and machine cannot change the output; the suite pins byte-identical TSV for one seed and a different sample for another.

Traceability. For an off-panel row, source_row_lookup_hint is analysis_major_row=<row>;analysis_major_range=<low>-<high>;variant_index=<v>;search=<mode>. The row is located by binary search over that Analysis’s ragged/variant_index range and read back to check it; search=scan says the range was not ordered and was scanned instead, and analysis_major_row=absent (with sample_trace_row_absent, an error) says the variant is not in the Analyses its own support plane names.

Exclusive strata come from the exclusive ranking. concentration asks who holds the union and ranks by distinct variants; the sample asks whose exclusive variants to trace and ranks by exclusive variants. A contributor that holds a lot and shares all of it is not the same contributor as one whose variants nobody else observes, and sample.exclusive_analyses / sample.exclusive_publications state which ranking the strata used.

On-panel controls. The Dense Component and the Ragged Overflow partition the axis, so an on-panel variant carries no Overflow association and has no row to be attributed from. Its Analyses are dense/z’s cells instead – one per (panel variant, Analysis) – read a row at a time and named for the Analyses the sample is about: the leading exclusive contributors, then the publication strata’s Analyses, and, where none of those holds the cell, the lowest-indexed Analysis that does (rows_naming_a_fallback_analysis counts them). Their hint is dense_row=<r>;dense_plane=z;analysis_index=<a>, which is the cell itself. A panel variant no Analysis holds is skipped and counted (panel_variants_skipped), and where the plane itself is unavailable (available: false) the controls are skipped rather than emitted with a blank where an Analysis should be.

The trace

trace answers one row at a time, for every row of a written sample: which raw source row is this, what frequency does it report, and what did the admission rule do with it? Four steps, in this order, each recorded rather than summarised:

  1. The source file. The Analysis’s build-manifest row gives source_file; when that path is gone, the source_url tail is mapped into the mirror under --raw-root. The file’s size and mtime are recorded, its declared checksum is quoted, and its declared source_genome_build must agree with the Store’s reference_assembly – a build that needed a lift would need a lift here too, and the trace does not perform one silently.

  2. The raw row. Each source file is read once, start to finish, however many sample rows it supplies. A requested site is (chromosome, position, allele pair), and every row at the position whose allele pair is the sample’s is kept, not just the first: a multiallelic site can hold several, and two rows can carry the same alleles with different frequencies. All candidates are retained in location.candidates, and their frequencies compared after orientation: candidates that agree describe one frequency reported twice and the row is traced from the first; candidates that disagree make the row ambiguous_source (source_row_ambiguous, an error) rather than resolved by first-seen order, and its admission is left unreplayed. The report records the physical line_number, the data_row, candidate_rows, raw_rows_at_position, allele_mismatch_rows (rows at the same position with other alleles), the source’s own column positions for the columns it read, and the raw effect_allele_frequency, beta, standard_error, p_value (and odds_ratio/ci_lower/ci_upper/rsid, and the Analysis’s declared imputation_score_column, when present) tokens verbatim. orientation is same when the source’s effect allele is the canonical A1 (the alphabetically first allele, as opengwasdb.variants.normalise.orient_to_canonical defines it) and flipped when it is the A2, in which case the frequency the builder stores is 1 - af.

  3. The frequency. The class of the raw token and the value opengwasdb.stats.parse_af reads from it. The classes are a closed vocabulary because the four ways a source says “no usable frequency” all reach the rule as the same NaN and must not be reported as one thing:

    Class Token parse_af
    placeholder_zero a number equal to 0.0 None (stores #176: a monomorphic site, or a placeholder; dropped by a filtered policy, opengwasdb#331)
    placeholder_one a number equal to 1.0 None (likewise)
    missing blank, ., NA, NaN, None, … None
    malformed unparseable, e.g. abc None
    nonfinite inf/-inf None
    out_of_range a finite number outside [0, 1], e.g. 1.5 None
    below_threshold a number in (0, 1) whose MAF is < maf_threshold the number
    valid_common a number in (0, 1) whose MAF is >= maf_threshold the number

    valid_common is the intended 0.005 <= MAF <= 0.995 interval at the 0.005 policy, with the boundary inclusive on both ends: af = 0.005 and af = 0.995 pass, af = 0.0049 and af = 0.9951 do not (the suite pins all four through the real builder, plus inf for nonfinite). A numeric class is decided by the MAF threshold alone, never by the disposition: a row only the INFO score drops still has a valid_common frequency, and reporting it below_threshold would blame the wrong rule.

  4. The admission. One call to opengwasdb.build.row_admission.admit_rows – the rule the Hybrid builder itself applies to a column of rows – over a batch of one, with the parsed frequency (NaN where there is none) and the declared INFO score parsed from the declared imputation_score_column. That column is not part of GWAS-SSF’s fixed vocabulary, so it is passed to the scan per Analysis: without it the score would read as missing and the declared INFO filter would silently keep every row. The MAF and INFO policies are parsed from the same manifest columns the build parsed (parse_maf_policy, parse_info_score_policy) and checked against what the Store recorded under provenance.maf and provenance.info_score – state and threshold: two filtered INFO policies at 0.8 and 0.9 agree on their state and keep different rows, so a threshold disagreement is an error, never a replayed preference.

The Store’s side of the same row is read, not assumed: its identity is the Variant Table row at the sample’s variant_index (cross-checked against the sample’s ALID), presence is the encoding’s own sentinel (Z_MISSING for z; on a Dense-axis control the cell is dense/z), and the stored frequency is reported as the plane’s stored code with whether it is the codec’s EAF_ABSENT (-128 on an int8_residual plane, NaN on a float16 one). It is deliberately not decoded: a residual is lossy and an absent code is the only answer a boundary question should ever take from it.

Dispositions. Every sampled row carries exactly one, from a closed vocabulary, and the tally is asserted to sum to the sample:

Disposition Meaning
valid_common the rule kept the row and its MAF is at or above the threshold
maf_below_threshold the rule dropped the row for its MAF
maf_missing the row carries no usable frequency – a placeholder, a blank, a malformed or an out-of-range token. Under a filtered MAF policy the rule drops it for that (opengwasdb#331); under disabled or unavailable it keeps it, unjudged. The frequency.class beside it says which token it was
info_below_threshold the rule dropped the row for its declared INFO score
unlocated_source the source file was read but holds no row at this position with this allele pair
ambiguous_source the source file holds more than one row at this position with this allele pair and their frequencies disagree, so the row cannot be replayed as one row
source_unavailable there is no readable source file, so the row cannot be judged

maf_missing is the bucket stores #380 repins for. admit_rows reads a frequency as usable evidence when it is finite and inside [0, 1]; a row it cannot read is no evidence a common-variant Store may admit, so a filtered policy drops it (opengwasdb#331, first shipped at the pinned 7308c6a). The same rule judges an exact 0.0/1.0 as a frequency whose MAF is 0 and drops it as below any positive threshold; because the reader still reports no stored EAF for one (parse_af, ADR 0036), what a real build hands the rule is NaN, so the build counts that row maf_missing – dropped for having no frequency. Either way the row leaves the Store, where before it stayed and grew the axis: a file-wide effect_allele_frequency = 0.0 placeholder was the cheapest possible way to do that.

The trace does not change that rule. It reports what the rule did, with the evidence a decision about it needs, and it reports the disagreement when a Store holds a row its own declared policy now drops: that is admission_disagrees_with_store, an error.

Read-only

Three properties, all checked rather than promised:

  1. The release is opened with opengwasdb.store.open.open_store and its arrays with arrays(mode="r"); every array is loaded mmap_mode="r". Nothing is written but --output, which may not be inside the Store.
  2. Every file’s size and mtime – and its sha256 unless the Store exceeds the hashing limit – is recorded before and after the audit and compared. A difference is an error (store_modified) and exits 1; the report says which method it used, so “unchanged” is a claim with a measurement behind it.
  3. The evidence file is written through tempfile.mkstemp in the output’s own directory and renamed onto --output with os.replace. A predictable .tmp sibling can pre-exist as a file or a symlink for this run to truncate; an unguessable one cannot. The staged path is checked against the Store before a byte is written, and a symlink already at --output is replaced rather than followed. trace additionally refuses an --output that resolves to its --sample, its --manifest or any raw source file it located: those are inputs, and an audit that overwrote one would destroy the row it was tracing.

Large artifacts stay outside Git, under the deployment’s evidence directory named in the ticket. Small reviewed reports may be committed.

Measured on OGS-00011

OGS-00011 is the Store epic #371 is about: a rebuilt Observed-Only Hybrid Store Release with 3,169 Analyses, built by opengwasdb revision 496bfe9cc9bbc85c60718d62aa4c6d43d83af810 (recorded in records/build.json). The audit took 334.9 s wall and 7.1 GiB peak RSS (resources.max_rss_kb 7,494,776) on a 224-core host, read 22,699 files without changing one (unchanged.method: size+mtime_ns), and reconciled:

  • 114,514,113 shared-axis variants = 13,415,936 Dense-axis + 101,098,177 off-panel, all three against the recorded counts;
  • 2,908,357,117 Overflow associations, the recorded total, with 0 on the Dense-axis side;
  • 101,098,177 off-panel entries observed and 0 unobserved – every off-panel axis entry carries at least one surviving observed association;
  • 0 duplicate ALIDs over 114,514,113 distinct canonical identities, 2,526,751 multiallelic sites covering 6,002,327 rows, and 1,273,627 rows with no rsid;
  • 29,789,554 of the 101,098,177 off-panel entries (29.5%) carry exactly one association, the single-observer tail the epic’s later tickets attribute;

The run’s store.stable_view shows why it still judged the view stable while a workflow/release.py OGS-00011 --config force=1 run from another epic held this release’s lock the whole time. A release whose lock outlives its run is an operational fact about that release; withholding a reconciliation that measured the Store twice and found it the same would hide it rather than report it.

The number to carry forward is the occupancy: the off-panel axis is not a tail of unused pre-filter identities. Something admitted 101,098,177 distinct variants and observed every one of them, which points the epic’s remaining hypotheses at admission and at source frequencies, not at axis bookkeeping.
