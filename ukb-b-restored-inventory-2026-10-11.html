Restored full UKB (ukb-b) Source Inventory and candidate — acceptance report (#219)

Snapshot ukb-b-restored-2026-10-11. Branch ticket/219-restored-ukb. This is Phase B evidence only: it freezes and reconciles the restored input set and emits a candidate Release Bundle to a staging directory for explicit human acceptance. No Store is built, completed, accepted, validated or published, and no candidate is registered in stores/.

Why this exists

The registered OGS-00009 observed Store and its OGS-00010 descendant contain 2,024 Analyses because 490 declared ukb-b Analyses had not finished copying into /data/opengwasdb/raw/gwas-vcf/ukb-b. The ticket requires the restored set to be reconciled against the declared intention, frozen with file identity, compared with the incomplete baseline, and emitted as a candidate — without assuming the final total.

Analytical Metadata resolution (offline provider JSON)

The stored OPENGWAS_JWT expired 2026-08-21, so POST /api/gwasinfo returns HTTP 401. Each ukb-b Analysis instead carries a provider JSON sidecar (<id>.json) holding the same study-level fields the API served. resources/generators/ukb-b/provider_metadata.py resolves the frozen inventory from those sidecars with an exact-ID check (json.id must equal the frozen analysis id), a batch check (ukb-b), each JSON’s sha256 recorded, and the same contract as the live resolver’s opengwas_api.R (unit → stored_effect_scale; a usable ncase/ncontrol pair → case_control, otherwise sample_size → total).

Result: 2,514 / 2,514 resolved, 0 unresolved, all batch = ukb-b, all population = European. The cross-check against the recorded opengwas-api-r2026-08-10 resolution is reported honestly as shared ids 2,514 / evaluated 2,511 / skipped 3 (ukb-b-12026, ukb-b-1226, ukb-b-1585 — recorded exclusions whose compared fields are all blank), with 0 disagreements on the 2,511 comparable rows. The three skipped rows are provider-only independent resolutions, not crosschecked matches: the receipt records per-field coverage as well (stored_effect_scale/sample_size_kind/ sample_size compared 2,511, missing 0; n_cases/n_controls compared 1,844, missing 667 because total-kind rows have no case/control counts). This dispositions the three historical exclusions from frozen local metadata rather than defaulting or dropping them, so the restored membership is a strict superset of the old build. A ncase+ncontrol that disagrees with the provider’s declared total N is surfaced in resolution_notes, never silently reconciled; retention of the provider’s total N preserves the total-vs-effective-N distinction. These are staged admission values pending human acceptance, not accepted membership.

Ancestry is the provider’s own population label with method source_fallback — not an AF-based assignment, and never the parent’s legacy source_trusted_no_af (the ukb-b VCFs demonstrably carry FORMAT/AF). af_assigned is not claimed and validation.yaml keeps checks.ancestry: not_run with the gap visible.

Candidate Release Bundle — staged, not registered

The orchestrator reserved the administrative candidate identities OGS-00030 (observed) and OGS-00031 (Reference-Completed); OGS-00017/OGS-00018 remain unallocated for MVP/FinnGen. Per the release gate, the candidate is not published into stores/: it is emitted to /data/opengwasdb/work/epic232/219/candidates/OGS-00030/ and validated there.

  • OGS-00030 — restored full ukb-b observed (dense, observed_only, status: candidate), membership = the frozen 2,514-row inventory, 2,514 buildable, 0 exclusions in the provider-resolution stage. It passes bundle.check() with no errors and no tolerated gaps and the shared OpenGWASDB analyses.tsv schema, and refuses to overwrite an existing bundle.
  • OGS-00031 is not emitted.   • OGS-00009 / OGS-00010 remain untouched historical incomplete baselines.

The candidate takes every source path, size and sha256 from the frozen inventory — never from a recorded resolution table, which still names another host’s /local-scratch paths.

Limitations and blockers (not silent substitutions)

  1. Live API resolution is unavailable (expired token). The offline provider JSON fallback is exact-ID checked, sha256-bound and cross-checked against the recorded API resolution, which is why it is a disposition rather than a substitution. Any later live re-resolution must reconcile against it.
  2. One-pass resolve-analyses cannot stream GWAS-VCF — but that is not the whole story. Two independent ten-Analysis runs returned 10/10 controlled_failure with TypeError: GwasVcfReader cannot stream source metrics; the one-pass resolver reads tabular sources only (issue #207) and rows_read = 0: the first on the default shared env’s 7b0c42d build, the second on the verified immutable #218 runtime (1be2a156…). The code branch (opengwasdb/build/resolve.py requires a MetricsReader; GwasVcfReader is not one) explains it structurally, so it is not runtime-version-specific. The focused core follow-up is #278 (one-pass resolver cannot stream GWAS-VCF metrics); #207 is the historical SSF-foundation issue (merged via #210), not current implementation scope, and #277 (assign-ancestry liftover) remains current. This must not be read as “all AF-based ancestry/SD is impossible”. The committed core exposes separate commands that DO read GWAS-VCF — but the ancestry command as invoked is assembly-incompatible for ukb-b (GRCh37 source vs GRCh38 reference, no liftover); see the measured section below. Evidence: /data/opengwasdb/work/epic232/219/resolution/probe-report.json.
  3. The declared EUR reference-AF resource is absent on this host. ukb-hg38-eur-af (/data/opengwasdb/reference/ukb-hg38) and gpm-hg38-eur-ld do not exist here, so the reference-MAF SD tier and the production completion panel are unavailable. Reported, not substituted.
  4. Runtime adoption is #218’s. The hm3 Indexed Variant Subset in the staged recipe mirrors OGS-00009; the format-0.2.0 runtime is adopted by #218 before #222 builds.

AF-based ancestry and SD via the separate supported core commands (measured)

The committed core provides assign-ancestry (default reader opengwasdb.gwas-vcf, targeted AF extraction at reference sites) and estimate-phenotype-sd (reads a canonical analyses.tsv through a SourceReader, source AF by default), both covered by committed tests. That is a failed pilot outcome, recorded as such: it is not a clean gate pass and not evidence that the threshold is wrong, so the threshold is untouched. A structural assembly gap (below) means the NNLS values are not interpretable as calibration evidence either. The full 2,514-Analysis ancestry run was NOT run and is not authorised (projected ≈57 h ancestry + ≈8 h SD). No source_fallback → af_assigned admission, no beta/SD override and no gate change is made; any such owner decision needs explicit approval. OGS-00031’s completion reference remains blocked.

Assembly / liftover convention — the decisive check. The ukb-b VCFs are GRCh37/hg19 (##contig=<ID=1,…,assembly=GRCh37>), the ancestry reference is GRCh38/hg38 (ref_freqs.hg38.tsv.gz, 5,810,530 sites). The assign-ancestry CLI exposes no --liftover/--chain option, annotate_catalogue calls assign_from_source(...) with no liftover, and GwasVcfReader.liftover defaults to None, so extract_at_sites built a -R regions file from the hg38 reference ALIDs and queried the hg19 VCF at those coordinates. Source and reference coordinates were therefore never aligned, and the ~0.5–0.8 % overlap (29.8k–45.5k / 5.81 M) is consistent with coincidental allele matches. The gate_reason=residual and eaf_orientation=passed values are artifacts of the assembly mismatch, not a gate/calibration finding, and are not used to change the candidate. The core library does document the correct path — assign_from_source(..., liftover=load_liftover(chain_file=…)), the chain file is present at /data/opengwasdb/reference/liftover/hg19ToHg38.over.chain.gz, and when set the reader does a full unrestricted scan lifting each row — but the CLI does not wire it. So the existing route is VCF-capable in principle yet assembly-incompatible as invoked, and the fix is liftover wiring (a small core CLI change) or a registry-side pre-lift, not loosening a threshold. The SD estimate is unaffected: --af-source source is assembly-independent and used a bounded evidence sample. Linear projection at 2 workers for the full 2,514: ≈57 h assign-ancestry + ≈8 h estimate-phenotype-sd (and a liftover run would be a full scan, so likely more for ancestry) — a material #222 budget item. Ancestry in the staged candidate stays source_fallback; no AF assignment was admitted. Evidence: resources/inventories/ukb-b-ancestry-sd-trial-2026-10-11.json (with manifest/reference/chain sha256 identities) and the work-dir copy at /data/opengwasdb/work/epic232/219/resolution/ancestry-sd-trial.json.
